# internal/di

The application's Loom dependency graph. `di.go` is regenerated by `weld add`
for the installed capability set and declares two things:

- `commonModule` — the providers every graph shares: the configuration loader,
  the configuration, the logger and the installed db/redis/mail/storage/events
  bindings. Every command graph includes it.
- `appGraph` (only when `http` is installed) — the server graph:
  `commonModule` plus the installed business modules, the server-only cron
  scheduler, the HTTP server and the application root. Loom generates `InitApp`
  from it.

`loom_gen.go` is Loom output and must never be edited by hand. The provider
seams are the opposite: weld writes `providers.go`,
`redis_provider.go`, `mail_provider.go`, `storage_provider.go`,
`jwt_provider.go` and `cron_provider.go` once and never regenerates them, so
they are the files you
edit to wire dependencies. `providers.go` is the single extension point for
custom services, repositories and third-party clients; its `projectModule` is
included by every graph, with unused providers pruned:

```go
// internal/di/providers.go, after `weld add db`
var projectModule = loom.Module(
	loom.As[data.Repository](NewRepository),
)
```

## What Loom binds, and why

| provider | installed when | bound to |
| --- | --- | --- |
| `*Config` | always | an immutable config built by `NewConfig`: the listen address (`serve --addr`, else `:8080`). The database fields are loaded but validated only by the pool |
| `logging.Logger` | always | `NewLogger`, which builds the base `logging` handler on stderr; injected into the server so startup, a serve failure and a shutdown are logged through one protocol, with no process default logger |
| `*pgxpool.Pool` | `db` | `data.NewPool`; **declared but not part of the default composition**. Loom prunes it while no provider depends on the pool — directly on `*pgxpool.Pool` or through a repository registered in `projectModule` (see `providers.go`). When such a consumer exists Loom validates the database section, parses the dsn lazily (it is **not** connected at build, test or startup) and registers a cleanup that closes it exactly once |
| `data.Repository` | `db` | **not declared by default**: the project registers it in `providers.go` (`loom.As[data.Repository](NewRepository)`), so `NewPool` and the repository are constructed only for the roots that consume it. The generated graph claims no production consumer until you register one |
| `*redis.Client` | `redis` | `redisclient.New` through `NewRedisClient`, defined in the stable `redis_provider.go` seam; **declared but not part of the default composition**. Loom prunes it while nothing depends on `*redis.Client`. When a consumer asks for it, Loom validates the `redis` section, builds the lazy client (it is **not connected** at build, test or startup) and registers a cleanup that closes it exactly once |
| `*mailsender.Sender` | `mail` | `mailsender.New` through `NewMailSender`, defined in the stable `mail_provider.go` seam; **declared but not part of the default composition**. Loom prunes it while nothing depends on `*mailsender.Sender`. Construction never connects and never sends |
| `*objectstore.Store` | `storage` | `objectstore.New` through `NewObjectStore`, defined in the stable `storage_provider.go` seam; **declared but not part of the default composition**. Loom prunes it while nothing depends on `*objectstore.Store`. Construction never connects |
| `*jwtauth.Manager` | `jwt` | `jwtauth.New` through `NewJWTAuth`, defined in the stable `jwt_provider.go` seam; **declared but not part of the default composition**. Loom prunes it while nothing depends on `*jwtauth.Manager`, so an ordinary serve needs no JWT secret. A consumer makes Loom validate the `jwt` section before startup; the manager holds an immutable key and has no lifecycle |
| `*cron.Scheduler` | `cron` | `cron.New` through `NewScheduler`, defined in the stable `cron_provider.go` seam. Unlike the bindings above, the server graph root consumes it, so Loom always constructs it and its start/stop hooks run with the server. `NewScheduler` takes the server, so the socket is bound before the scheduler starts and the scheduler stops before the server. `NewCronJobs` in `internal/di/cron_jobs.go` injects services and binds their methods before startup. It starts no jobs unless that seam registers them |
| `*httpserver.Server` | `http` | the framework-neutral runtime built with the shared `httpserver.NewHandler`; DI attaches `Start(ctx)` and `Stop(ctx)` to Loom hooks |
| `*App` | `http` | the server graph root returned by `InitApp` |

`internal/di` is the only package that knows the whole composition. The
capabilities stay independent: `internal/data` never imports `net/http`, and
neither `db` nor a business module imports Loom.

Because `http` requires `loom`, a project that installs `http` always has both;
a project that installs only `db`, `redis`, `mail`, `storage`, `config` or a
command has Loom and `commonModule` but no server graph, no `InitApp` and no
`internal/httpserver`.

## Custom providers

Declare project-specific providers in `internal/di/providers.go`, then run
`make generate`. Use `loom.Provide(NewClient)` for a concrete result or
`loom.As[SomeInterface](NewImplementation)` for an interface binding.
Declare them once; every graph can consume them without copying registrations.

HTTP policy wiring lives in `internal/di/http_policies.go`: add service
parameters to `NewHTTPPolicies` and return named middleware. Route constants
remain in `internal/httpserver/policy.go`; mount prefixes live in
`internal/httpserver/mounts.go`, and error mapping in `internal/httpserver/errors.go`.
The default admin policy denies all requests until real authentication and
administrator authorization are configured. Never import business services into
httpserver, which the business modules themselves reference. See
`internal/httpserver/README.md` for handler composition and testing.

## The database is wired by hand

`weld add db` installs a capability, not a connection. The graph declares the
pool provider above but registers no `data.Repository` by default, so Loom
prunes the pool and no command needs a database credential. When you want
persistence, register the repository in `providers.go`, the
project-owned seam, rather than in `di.go`, which is regenerated:

```go
// internal/di/providers.go, after `weld add db`
var projectModule = loom.Module(
	loom.As[data.Repository](NewRepository),
)
```

Then make a provider the graph consumes ask for it — for a server project, edit
the `service.go` of one of your business modules (the module graph binds its
`NewService`):

```go
// internal/modules/<name>/service.go, after `weld add db`
func NewService(repo data.Repository) Service {
	return &repositoryService{repo: repo} // your repository-backed Service
}
```

Loom infers the provider's dependencies from its signature: once a consumer asks
for `data.Repository`, Loom constructs `NewPool` and the registered repository
too. `NewPool` validates the database settings, so the credential is required
only when the pool is actually built. See `internal/data/README.md` for the pool,
repository and transaction seams.

### Redis, mail and storage follow the same pattern

`weld add redis`, `weld add mail` and `weld add storage` declare an available
binding (`NewRedisClient`, `NewMailSender`, `NewObjectStore`) in their stable
provider seam, and the graph declares them but nothing depends on them, so Loom
prunes them and an ordinary command needs no Redis, mail or storage setting. To
use one, make a provider the graph already consumes depend on it — for a
server project, edit a business module's `NewService` in the same way. They
never connect at construction. See
`internal/redisclient/README.md`, `internal/mailsender/README.md` and
`internal/objectstore/README.md`.

### Cron is wired, not pruned

`weld add cron` is different: the server graph root consumes `*cron.Scheduler`,
so Loom constructs `NewScheduler` and registers its `loom.Hook` start/stop.
`NewScheduler` takes the `*httpserver.Server`, and Loom constructs providers in
dependency order and appends hooks as it constructs them, so the socket is bound
before the scheduler starts and the scheduler stops before the server.
Add service parameters and register their `func(context.Context) error` methods
in `NewCronJobs` in `internal/di/cron_jobs.go`, then run `make generate`.
Registration is automatic before startup; no job dependency bundle is needed.
The scheduler logs job errors with their names. See `internal/cron/README.md`.

### Business event listeners are wired automatically

After `weld add events`, add consuming service parameters and `events.On` calls
in `internal/di/events_listeners.go`, then run `make generate`. The HTTP graph
consumes `*EventListeners` automatically before startup. A consuming service may
also inject `events.Publisher`; registration is separate from publisher creation.
Business listeners have one entry point: `internal/di/events_listeners.go`.
Command/seed graphs do not automatically register server listeners.
See `internal/events/README.md` for a publish-in-A, consume-in-B example.

Never wire providers into `di.go`: it is regenerated from the installed
capability set, and an edit there is erased by the next capability install.

## Command groups get their own graph

`weld add command <name>` and `weld add module <name> --command` write a stable
command graph in `internal/di/<name>_graph.go`. It includes `commonModule` — the
shared provider set `di.go` declares and `weld add` regenerates — plus the
command's dependency root, and it never includes the HTTP server or the cron
scheduler. Because the shared providers live in the regenerated module rather
than in the command graph, a capability installed *after* the command graph was
written still reaches the command: `weld add db` extends `commonModule`, and
every graph that includes it picks up the new binding without weld rewriting the
stable command graph. Loom prunes every provider the root does not consume, so a
short command constructs nothing beyond what its subcommands ask for, and there
is no process-wide singleton: each graph keeps its own instance cache.

The generated command package does not import the Loom runtime. It resolves the
graph through `internal/commandkit`, the shared seam shipped with Loom:
`commandkit.Run` builds and starts the graph only when a real subcommand runs,
runs the subcommand, stops the graph within a bounded deadline and joins any
teardown error. Help, `version` and every unrelated command never build the
graph.

`weld add` regenerates `di.go` for the whole installed set, so the command
graphs stay stable while `commonModule` grows with the project. To
consume a shared provider, add a field to the command root's `Deps` and a
parameter to `<name>.NewDeps`; it is already an available binding through
`commonModule`, so no graph edit is needed — a `data.Repository` the project
registered in `providers.go` reaches a command this way too. A
dependency no provider declares needs `loom.Provide(...)` in the command graph.
The server-only `*cron.Scheduler` is never available to a command.

### `di_test.go` is module-independent

The regenerated `di_test.go` never names a module: it exercises configuration,
the pool, the server lifecycle and the middleware chain, and
it builds those through the generated `newServer` seam rather than through a
module's `Service`. Each module
package tests its own routes in `internal/modules/<name>/module_test.go`, a file
written once and never regenerated. The consequence is that installing a module
refreshes `di.go` and `loom_gen.go` but leaves `di_test.go` byte-for-byte
unchanged, and changing `NewService` to take a dependency (for example
`NewService(repo data.Repository)` after `weld add db` and registering the
repository in `providers.go`) cannot break the graph
test. Keep
module-specific assertions in the module's own test, not here: `di_test.go` is
generated and an edit to it does not survive the next `weld add`.

## Configuration

Configuration does not scatter `os.Getenv` through providers: `NewConfig`
receives the injected loader, applies the file, the environment, the defaults
and the `--addr` context override when `http` is installed, and returns an
immutable `*Config`. The database section is read into `*Config` but validated
only by `NewPool`, so installing `db` without using it never requires
`DATABASE_URL`. When the pool is built, a missing credential fails loudly rather
than inventing a default dsn, and an error never echoes the dsn.

The server binds the listen address synchronously: a port already in use makes
`lifecycle.Start` fail, and a serve failure is reported to the serve command so
it stops instead of waiting forever. When the pool is constructed, Loom runs its
cleanup exactly once whether construction later fails or the lifecycle stops.
HTTP shutdown honors the lifecycle context; if draining is canceled or exceeds
its deadline, the runtime closes active connections before returning the error.

Because the graph references concrete capability packages, installing a
capability regenerates `di.go` and `loom_gen.go` for the new capability set; the
composition is capability aware and order independent.

## Go toolchain floor

The generated initializer imports `github.com/Xwudao/loom`, whose module
requires Go 1.25. Installing `loom` therefore raises the project's Go directive
to `go 1.25.0`. The generator itself is pinned in `tools/loom`, a nested module,
so its `x/tools` dependency never enters this module.

## Regenerating

```sh
make generate
```

`weld add` regenerates `di.go`, `di_test.go` and `loom_gen.go` for you when an
installed capability changes the provider set; re-adding an installed capability
(for example `weld add loom`) reconciles them when only the templates changed, so
a project scaffolded by an older weld can be refreshed in place — including a
stable seam a newer weld added, such as `providers.go`. Do not edit
these generated files. The stable provider seams — `providers.go`,
`redis_provider.go`, `mail_provider.go`, `storage_provider.go`,
`jwt_provider.go` and `cron_provider.go` — are written once and never
regenerated, so edit those
files to wire dependencies, and keep a module's own route assertions in that
module's `module_test.go`.

## Tests

`di_test.go` exercises the generated composition with no PostgreSQL:
configuration is driven through an injected loader and the lifecycle's bind,
serve-failure and
graceful-stop behavior is checked on loopback sockets. The lifecycle tests inject
a logger backed by an `io.Discard` or in-memory writer, so startup and shutdown
logging is asserted without touching the process streams. The file is
module-independent, so a new module adds its routes to the module's own test and
never to this one. A CLI-only project (no `http`) gets only the configuration
tests.
